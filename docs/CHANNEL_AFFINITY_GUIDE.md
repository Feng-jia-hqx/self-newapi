# New API 多渠道高可用与缓存加速配置指南（渠道亲和）

> 适用场景：同一模型接入多个上游渠道（如多套智谱 Max 套餐、多家供应商聚合），需要**负载均衡 + 故障自动切换 + 会话粘性**（最大化命中上游 Prompt Cache）三者的组合。
>
> 本指南在 v1.0.0-rc.21+ / latest 镜像上验证。旧版本无 `request_header` Key 来源，升级后再按本文配置。

## 一、核心架构目标

| 目标 | 实现机制 |
|------|---------|
| **宏观均衡** | 多渠道相同优先级 + 相同权重，请求在渠道间加权随机分摊 |
| **微观粘性（渠道亲和）** | 每个令牌的会话固定路由到同一渠道，命中上游服务端 Prompt Cache，降低首字延迟与成本 |
| **自动容灾** | 首选渠道 429/故障时自动重试切换备用渠道；成功后亲和绑定平滑迁移到新渠道；渠道被禁用时绑定自动失效重绑 |

**工作原理一句话**：分发时先按"亲和值"（默认=令牌 ID）查缓存，命中且渠道可用 → 直接用该渠道；未命中或渠道不可用 → 走正常加权随机，成功后把「亲和值 → 渠道」写入缓存（默认 TTL 1 小时）。实现见 `middleware/distributor.go` 与 `service/channel_affinity.go`。

---

## 二、第一步：配置"路由可靠性"（429 自动重试的前提）

进入 **系统管理 → 模型与路由 → 路由可靠性**：

- **重试次数（Retry Times）**：设为 **`1`**（范围 0–10）。
  默认值是 **0** —— 不改这个，任何渠道故障都不会自动切换，亲和的高可用就是空谈。
  双渠道设 1 恰好（A 失败 → B）；N 个渠道建议 N-1。
- **自动重试状态码（Auto-retry status codes）**：默认已含 429（409–499 段），保持默认。
- 点击 **保存更改**。

> ⚠️ **永不自动重试的状态码**：`504`、`524`（上游网关超时）和 `400`、`408`。上游长时间无响应时客户端会直接收到错误，这是设计行为，不要误判为容灾失效。

## 三、第二步：配置"渠道亲和性"

进入 **系统管理 → 模型与路由 → 渠道亲和性**，点击 **添加规则**：

| 字段 | 填写值 | 说明 |
|------|--------|------|
| 名称 | `per-token sticky`（自定义） | 仅作标识，会出现在日志与缓存统计中 |
| 模型正则 | 每个模型族一行（见下方速查表） | 如 `^glm-.*$`；支持多行，任一匹配即生效 |
| 路径正则 | 留空 | 对所有 API 路径生效 |
| Key 来源 | `context_int` : `token_id` | **推荐**。按令牌数字 ID 绑定，无敏感信息 |
| TTL（秒） | `86400`（按需） | 不填则取全局默认 **3600（1 小时）**，会话超时后粘性失效 |
| 失败后不重试 | **关闭** | 开启会破坏高可用（亲和渠道失败后不再切换） |
| 包含模型名 | 按需 | 见下方说明 |

**Key 来源选型**（重要）：

| 方案 | 绑定粒度 | 安全性 | 建议 |
|------|---------|--------|------|
| `context_int` : `token_id` | 每个令牌 | ✅ 无敏感信息 | **首选** |
| `context_string` : `token_name` | 每个令牌 | ✅ 无敏感信息 | 需要在日志中直观看到令牌名时用 |
| `request_header` : `Authorization` | 每个令牌 | ⚠️ **完整令牌明文（`Bearer sk-...`）会作为缓存 key 写入 Redis**，任何能读 Redis 的一方都能拿到令牌 | 仅单机内存缓存（无 Redis）时可接受 |

三种方案绑定效果完全相同（同令牌同渠道），优先选前两种。

**「包含模型名」开关**：
- 关（默认）：同一令牌的所有模型粘同一渠道。
- 开：同一令牌在不同模型（如 `glm-5` 与 `glm-5-air`）各自独立粘渠道。
- 双套餐模型列表完全一致时两者皆可；**日后按模型差异化权重/渠道时建议开启**。

**全局面板开关**：

| 开关 | 状态 | 作用 |
|------|------|------|
| 启用 | ✅ 开 | 亲和功能总开关 |
| 成功后切换亲和（Switch on success） | ✅ 开 | 渠道 A 限速、重试成功走到渠道 B 后，绑定自动迁移到 B，下次请求直接走 B |
| 渠道禁用时保留亲和（Keep on channel disabled） | ❌ 关（默认） | 关闭 = 手动禁用某渠道时，其上的存量绑定立即清除并重绑到可用渠道（维护场景的平滑迁移靠它） |

## 四、第三步：检查渠道基础配置

进入 **管理员 → 渠道**，检查同一模型的各渠道（渠道 A / 渠道 B）：

- **模型列表**：各渠道勾选的模型保持一致（否则亲和命中后可能因渠道不支持该模型而回退随机）。
- **优先级（Priority）**：设相同值（如都为 `0`）。优先级不同的渠道会形成主备梯队而非均衡分摊。
- **权重（Weight）**：设相同值（如都为 `100`）。亲和未命中时按权重随机分摊。

## 五、验证与观测

### 前置检查（改配置后必做）

1. 路由可靠性：**重试次数 = 1** 已保存（默认 0，忘改则容灾验证必失败）
2. 亲和性面板：**启用 ✅、成功后切换亲和 ✅**
3. 规则已保存：`context_int` : `token_id`、模型正则、TTL 86400
4. 渠道 A/B：模型列表一致、优先级相同、权重相同
5. **按规则清空一次缓存**（清掉迁移前 `Authorization` 时代的明文残留条目）

### 第 1 步：绑定生成

用员工的 API 令牌从外部发一次请求：

```bash
curl -s https://你的域名/v1/chat/completions \
  -H "Authorization: Bearer sk-员工令牌" \
  -H "Content-Type: application/json" \
  -d '{"model":"glm-5","messages":[{"role":"user","content":"你好"}]}'
```

刷新"渠道亲和性"页面 → **缓存条目 +1**。

> ⚠️ **不要用控制台 Playground 验证**：Playground 走 session 认证，请求上下文中没有 `token_id`，亲和规则不会命中。必须用 API 令牌从外部调用。

### 第 2 步：会话粘性

同一令牌连续发 3–5 次请求 → **通用日志** 筛选该令牌：

- **通过标准**：从第 2 次起，所有请求的渠道 ID 恒定（第 1 次未命中缓存、随机分配属正常）
- 打开日志详情，`channel_affinity` 信息块应显示：`key_source: context_int`、`key_hint: 令牌数字ID`、`channel_id: 固定值`

### 第 3 步：缓存命中（收益验证）

同一令牌、相同上下文前缀发多轮对话：

- 用量日志中查看该令牌的缓存命中指标（cached tokens / prompt cache 命中），从第 2 轮起应明显上升
- 亲和统计可按 规则名/分组/Key 指标 查看窗口内命中率与缓存 token 累计

### 第 4 步：容灾切换

| 方法 | 操作 | 通过标准 |
|------|------|---------|
| A. 禁用渠道 | 管理员 → 渠道 → 禁用渠道 A，同令牌再发请求 | 请求成功，日志显示渠道 B；绑定自动重绑到 B |
| B. 模拟故障 | 把渠道 A 的密钥改成无效值再发请求 | 请求 **HTTP 200**（自动重试到 B，客户端无感）；因"成功后切换亲和"开启，后续请求直接走 B |

**恢复渠道 A 后的行为**：存量绑定**留在 B，不会自动回迁**（预期行为，避免反复横跳）；A 继续承接新令牌和绑定过期后的重分配。

### 验证不通过时的排查

| 症状 | 原因 |
|------|------|
| 缓存条目不增长 | 用了 Playground（无 token_id）；模型正则不匹配实际请求的模型名；规则未启用 |
| 请求渠道总是随机 | 亲和未命中 → 检查正则与模型名拼写；绑定 TTL 已过期（重新分配属正常） |
| 容灾时直接报错不切换 | 重试次数仍为 0；失败状态码不在自动重试范围（如 504/524 永不重试） |
| 缓存条目统计看不到本规则 | 统计按规则名分组，规则需开启 **包含规则名**，否则计入 unknown |
| 员工换了令牌后换了渠道 | 绑定粒度是令牌，新令牌 = 新绑定 = 重新分配（预期行为） |

## 六、扩展到其他模型（正则速查表）

模型正则一个模型族一行，可同时配多行。常用模型族：

| 模型族 | 正则 |
|--------|------|
| 智谱 GLM 全系 | `^glm-.*$` |
| Anthropic Claude | `^claude-.*$` |
| OpenAI GPT | `^gpt-.*$` |
| Gemini | `^gemini-.*$` |
| 通义千问 | `^qwen-.*$` |
| DeepSeek | `^deepseek-.*$` |

> ⚠️ **与内置规则的关系**：系统默认自带 `codex cli trace`（`^gpt-.*$` + `/v1/responses`）和 `claude cli trace`（`^claude-.*$` + `/v1/messages`）两条规则，按数组顺序匹配、命中即停。自定义规则追加在末尾即可：带路径限定的内置规则先匹配（CLI 场景），其余请求落到你的通用规则，互不冲突。

## 七、注意事项与常见问题

| 问题 | 说明 |
|------|------|
| 多节点部署 | 亲和缓存 = 内存 + Redis 混合。**多节点必须配置 Redis**（`REDIS_CONN_STRING`），否则各节点独立绑定，命中率打折。单机无 Redis 时仅内存缓存，功能正常 |
| 上游不支持 Prompt Cache？ | 亲和只是"把会话路由到同一渠道"，是否真有缓存收益取决于上游是否实现 Prompt Cache（智谱 GLM / Claude / Gemini / DeepSeek 等均支持） |
| 员工换令牌 | 绑定粒度是令牌：换令牌 = 新的亲和值 = 重新随机分配渠道（预期行为） |
| 想按"员工"而非"令牌"绑定 | Key 来源用 `context_int` : `id`（用户 ID），该员工所有令牌共享同一渠道绑定 |
| 绑定 channels 的容量 | 全局 `max_entries` 默认 100,000 条，超出按 LRU 淘汰 |
| 清空绑定 | 亲和性面板支持按规则名清空或全量清空（规则需开启"包含规则名"） |
